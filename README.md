# depviz

Небольшая консольная программа на Java, которая показывает, от каких пакетов зависит пакет NuGet
(менеджер пакетов .NET), и рисует граф этих зависимостей. Зависимости программа достаёт сама,
без готовых менеджеров пакетов и сторонних библиотек.

Это практическая работа № 2 по «Конфигурационному управлению», вариант 4.
Сейчас готовы четыре этапа: программа принимает настройки из командной строки, скачивает
зависимости из репозитория NuGet (или читает тестовый файл), строит полный граф зависимостей
с учётом транзитивности и показывает порядок загрузки пакетов.

## Как программа узнаёт зависимости

У каждого пакета NuGet есть файл описания `.nuspec` (это XML). Программа скачивает его
с репозитория по адресу `{repo}/{имя}/{версия}/{имя}.nuspec` и сама разбирает: берёт
список `<dependency>` из блока `<dependencies>`.

Если пакет или версия не найдены или нет связи с репозиторием, программа так и пишет
и завершается с кодом 3.

## Как строится граф

Граф строится рекурсивным обходом в глубину (DFS): программа берёт зависимости пакета,
потом зависимости каждой из них и так далее.

- **Глубина.** Корневой пакет – глубина 0, его прямые зависимости – 1 и так далее.
  Зависимости читаются только у пакетов на глубине меньше `--max-depth`. Пакеты на самой
  границе попадают в граф, но помечаются «не раскрыт».
- **Фильтр.** Пакеты, в имени которых есть подстрока из `--filter` (регистр не важен),
  пропускаются вместе со всем, что тянется только через них. Корневой пакет не фильтруется.
- **Повторы.** Если пакет уже встречался, второй раз он не обходится, в графе он один.
- **Циклы.** Если зависимость ведёт в пакет, который уже есть на текущем пути от корня,
  это цикл. Программа выводит такое ребро отдельно и дальше по нему не идёт, поэтому не зависает.

## Порядок загрузки

После графа программа печатает порядок загрузки: каждый пакет стоит после всех своих
зависимостей, корневой пакет – последний. Это топологическая сортировка: обход в глубину,
при котором пакет записывается в список, когда уже записаны все его зависимости.

Если в графе есть цикл, правильного порядка не существует: A нужно загрузить раньше B,
а B раньше A. Тогда ребро, замыкающее цикл, пропускается, а программа предупреждает,
что порядок для этих пакетов условный.

### Сравнение с настоящим NuGet

Для сравнения я создал пустой консольный проект (.NET SDK 10.0.403, платформа `net10.0`),
добавил в него пакет через `dotnet add package` и посмотрел, что выбрал NuGet
(`dotnet list package --include-transitive` и файл `obj/project.assets.json`).
По зависимостям из `project.assets.json` построил порядок тем же способом, что и программа.

Для `Microsoft.Extensions.Logging 8.0.0` dotnet подтянул 6 пакетов и порядок у него такой:
`DependencyInjection.Abstractions`, `DependencyInjection`, `Logging.Abstractions`, `Primitives`,
`Options`, `Logging` (все с префиксом `Microsoft.Extensions.`). У depviz пакетов 88: те же шесть
плюс десятки `System.*`, `runtime.*` и `NETStandard.Library`.

Для `Serilog.Sinks.Console 6.0.0` у dotnet всего 2 пакета: сначала `Serilog 4.0.0`, потом
сам `Serilog.Sinks.Console`. У depviz – 82.

Если оставить в выводе depviz только пакеты, которые есть и у dotnet, порядок совпадает
полностью, в обоих случаях.

Почему так:

1. **Фреймворк.** dotnet берёт из `.nuspec` только группу зависимостей для своей платформы
   (`net8.0` подходит для `net10.0`), а для неё у этих пакетов зависимостей почти нет.
   depviz объединяет группы всех фреймворков, в том числе `.NETFramework4.6.2` и `.NETStandard2.0`,
   откуда приходят `System.Memory`, `System.ValueTuple` и через них `NETStandard.Library`
   со всем набором старых системных пакетов.
2. **Версии.** NuGet выбирает одну версию на пакет, и если её требуют разные пакеты,
   берёт наибольшую из минимальных. depviz берёт ту версию, которую встретил первой.
   Поэтому у depviz в графе `Microsoft.Extensions.Logging` оказывается
   `System.Diagnostics.DiagnosticSource 4.3.0` (первый раз он встретился глубоко внутри
   `NETStandard.Library`), хотя сам Logging для старых платформ просит `8.0.0`.
3. **Что такое «порядок загрузки».** У NuGet нет отдельного порядка установки: restore
   скачивает пакеты параллельно, а .NET подгружает сборки при первом обращении. Порядок
   для dotnet я построил по его же графу тем же способом.

Расхождения возникают из-за того, что depviz не знает, под какую платформу собирается
проект. Если выбирать одну группу фреймворка, получится то же, что у dotnet, но такого
параметра в задании нет.

### Упрощения для NuGet

- В `.nuspec` зависимости разбиты по версиям .NET. Программа **объединяет зависимости всех
  фреймворков**. Поэтому у пакетов, которые поддерживают старый `netstandard1.x`, граф выходит
  большим: туда попадает `NETStandard.Library` и десятки системных пакетов, хотя для современного
  .NET они не нужны.
- Версия зависимости записана диапазоном, например `[1.6.1, )`. Как и NuGet по умолчанию, программа
  берёт **наименьшую подходящую версию**, то есть нижнюю границу.
- Каждый пакет хранится в графе **в одной версии** – той, что встретилась первой.
- Из-за первых двух пунктов в настоящем репозитории иногда находятся «циклы», которых нет
  для конкретного фреймворка. Например, у `Serilog.Sinks.Console 6.0.0` программа находит
  `System.Net.Http -> System.Diagnostics.DiagnosticSource`: путь к `System.Net.Http` идёт через
  `netstandard1.x`-зависимости, а `DiagnosticSource` уже есть выше в графе в версии 8.0.1.

## Настройки

Всё задаётся параметрами командной строки:

- `--package <имя>` – какой пакет анализировать. Обязательный параметр.
- `--package-version <версия>` – версия пакета, например `13.0.3`. Нужна всегда, кроме тестового режима.
- `--repo <адрес>` – откуда брать данные. По умолчанию это официальный репозиторий
  `https://api.nuget.org/v3-flatcontainer`. В тестовом режиме сюда пишется путь к файлу.
- `--test-mode` – работать не с настоящим репозиторием, а с тестовым файлом (о нём ниже).
- `--output <файл.svg>` – куда сохранить картинку с графом. По умолчанию `graph.svg`.
- `--ascii-tree` – дополнительно вывести зависимости деревом прямо в консоль.
- `--max-depth <n>` – насколько глубоко идти по зависимостям. По умолчанию 10.
- `--filter <подстрока>` – пропускать пакеты, в имени которых есть эта подстрока.
- `--help` – показать справку.

Значение можно писать через пробел (`--max-depth 3`) или через знак равно (`--max-depth=3`).

Если что-то задано неправильно, программа не падает, а объясняет, что не так, и завершается
с кодом 2. Например, она скажет, если забыли имя пакета, написали версию `latest`, указали
глубину `zero` или файл, которого нет.

### Тестовый репозиторий

Чтобы проверять программу без интернета, можно описать свой маленький «репозиторий» в текстовом
файле. Каждая строка – пакет и через двоеточие его зависимости. Пакеты называются заглавными
латинскими буквами, строки с `#` пропускаются:

```
A: B C
B: D
C: D
D:
```

Пакет, который упомянут только как зависимость, считается пакетом без зависимостей.
Готовые примеры лежат в папке [examples](examples):

- `basic.txt` – «ромб»: B и C оба зависят от D;
- `cycle.txt` – цикл A → B → C → A и пакет, зависящий сам от себя;
- `deep.txt` – длинная цепочка A → B → … → H для проверки `--max-depth`;
- `project.txt` – «приложение» с библиотеками для проверки `--filter`.

## Сборка и тесты

Понадобятся Java 21 или новее и Maven (на macOS ставится командой `brew install maven`).

```bash
make build   # собрать программу
make test    # запустить тесты
make clean   # удалить всё, что получилось при сборке
```

Запускать удобнее всего через `./run.sh`: он сам пересоберёт программу, если код поменялся.

## Примеры

### Тестовый репозиторий

«Ромб» – D попадает в граф один раз:

```
$ ./run.sh --test-mode --repo examples/basic.txt --package A
Граф зависимостей пакета A (пакетов: 4):
  A -> B, C
  B -> D
  D -> нет зависимостей
  C -> D
```

Циклы не мешают обходу и выводятся отдельно:

```
$ ./run.sh --test-mode --repo examples/cycle.txt --package A
Граф зависимостей пакета A (пакетов: 5):
  A -> B
  B -> C
  C -> A, D, E
  D -> нет зависимостей
  E -> E
Циклические зависимости:
  C -> A
  E -> E
```

Ограничение глубины:

```
$ ./run.sh --test-mode --repo examples/deep.txt --package A --max-depth 3
Граф зависимостей пакета A (пакетов: 4):
  A -> B
  B -> C
  C -> D
  D -> (не раскрыт: достигнута максимальная глубина)
```

Фильтр: без `TESTKIT` пропадают и `MOCK` с `ASSERT`, потому что к ним можно прийти только через него:

```
$ ./run.sh --test-mode --repo examples/project.txt --package APP --filter TEST
Граф зависимостей пакета APP (пакетов: 7):
  APP -> WEB, DATA
  WEB -> HTTP, JSON
  HTTP -> NET
  NET -> нет зависимостей
  JSON -> нет зависимостей
  DATA -> SQL, JSON
  SQL -> NET
```

Порядок загрузки для «ромба» (вывод графа выше пропущен): D нужен и B, и C, поэтому он первый:

```
$ ./run.sh --test-mode --repo examples/basic.txt --package A
...
Порядок загрузки (сначала зависимости, затем зависящие от них):
    1. D
    2. B
    3. C
    4. A
```

Для цикла порядок всё равно выводится, но с предупреждением:

```
$ ./run.sh --test-mode --repo examples/cycle.txt --package A
...
Порядок загрузки (сначала зависимости, затем зависящие от них):
    1. D
    2. E
    3. C
    4. B
    5. A
Внимание: в графе есть циклы, для пакетов из них правильного порядка не существует.
```

### Ошибки

```
$ ./run.sh --package Newtonsoft.Json
Ошибка: Не задана версия пакета: укажите --package-version <версия>, например 13.0.3

$ ./run.sh --test-mode --repo examples/project.txt --package NOPE
Ошибка: Пакет NOPE не описан в тестовом репозитории examples/project.txt

$ ./run.sh --package Newtonsoft.Json --package-version 99.0.0
Ошибка: Пакет Newtonsoft.Json версии 99.0.0 не найден в репозитории https://api.nuget.org/v3-flatcontainer
```
