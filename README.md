# depviz

## Общее описание

Небольшая консольная программа на Java, которая показывает, от каких пакетов зависит пакет NuGet
(менеджер пакетов .NET), и рисует граф этих зависимостей. Зависимости программа достаёт сама,
без готовых менеджеров пакетов и сторонних библиотек.

Это практическая работа № 2 по «Конфигурационному управлению», вариант 4. Готовы все пять этапов.

Что программа делает:

1. скачивает описание пакета из репозитория NuGet (или читает тестовый файл);
2. строит полный граф зависимостей с учётом транзитивности;
3. печатает граф в консоль – списком или ASCII-деревом;
4. сохраняет граф на языке диаграмм [D2](https://d2lang.com) и рисует по нему картинку SVG.

## Функции и настройки

Всё задаётся параметрами командной строки:

- `--package <имя>` – какой пакет анализировать. Обязательный параметр.
- `--package-version <версия>` – версия пакета, например `13.0.3`. Нужна всегда, кроме тестового режима.
- `--repo <адрес>` – откуда брать данные. По умолчанию это официальный репозиторий
  `https://api.nuget.org/v3-flatcontainer`. В тестовом режиме сюда пишется путь к файлу.
- `--test-mode` – работать не с настоящим репозиторием, а с тестовым файлом (о нём ниже).
- `--output <файл.svg>` – куда сохранить картинку с графом. По умолчанию `graph.svg`.
  Рядом появится файл с тем же именем и расширением `.d2` – описание графа на D2.
- `--ascii-tree` – вывести зависимости в консоль деревом, а не списком.
- `--max-depth <n>` – насколько глубоко идти по зависимостям. По умолчанию 10.
- `--filter <подстрока>` – пропускать пакеты, в имени которых есть эта подстрока.
- `--help` – показать справку.

Значение можно писать через пробел (`--max-depth 3`) или через знак равно (`--max-depth=3`).

Если что-то пошло не так, программа не падает, а объясняет, в чём дело. Код завершения
подсказывает, где ошибка: 2 – в параметрах, 3 – при получении данных о пакетах,
4 – при построении картинки.

## Как это работает

### Откуда берутся зависимости

У каждого пакета NuGet есть файл описания `.nuspec` (это XML). Программа скачивает его
с репозитория по адресу `{repo}/{имя}/{версия}/{имя}.nuspec` и сама разбирает: берёт
список `<dependency>` из блока `<dependencies>`.

Версия зависимости обычно записана диапазоном, например `[1.6.1, )` – «1.6.1 или новее».
Как и NuGet по умолчанию, программа берёт наименьшую подходящую версию, то есть нижнюю границу.

### Как строится граф

Граф строится рекурсивным обходом в глубину (DFS): программа берёт зависимости пакета,
потом зависимости каждой из них и так далее.

- **Глубина.** Корневой пакет – глубина 0, его прямые зависимости – 1 и так далее.
  Зависимости читаются только у пакетов на глубине меньше `--max-depth`. Пакеты на самой
  границе попадают в граф, но помечаются как нераскрытые.
- **Фильтр.** Пакеты, в имени которых есть подстрока из `--filter` (регистр не важен),
  пропускаются вместе со всем, что тянется только через них. Корневой пакет не фильтруется.
- **Повторы.** Если пакет уже встречался, второй раз он не обходится, в графе он один.
- **Циклы.** Если зависимость ведёт в пакет, который уже есть на текущем пути от корня,
  это цикл. Программа отмечает такое ребро и дальше по нему не идёт, поэтому не зависает.

### Визуализация

- **D2.** Каждый пакет – узел с версией в подписи, каждая зависимость – стрелка.
  Корневой пакет выделен цветом, нераскрытые пакеты нарисованы пунктиром, рёбра циклов –
  красным пунктиром с подписью «цикл».
- **SVG.** Картинку по описанию на D2 рисует утилита `d2`, программа просто запускает её.
  Запрет на готовые инструменты в задании касается получения зависимостей, а не рисования.
  Если `d2` не установлена, программа скажет об этом, а файл `.d2` всё равно сохранит.
- **ASCII-дерево.** Граф – не дерево: один пакет может понадобиться нескольким. Поэтому
  поддерево пакета раскрывается только при первом появлении, а дальше пакет помечается `(*)`.
  Циклы помечаются `(цикл)`, пакеты на границе глубины – `(...)`.

### Упрощения для NuGet

- В `.nuspec` зависимости разбиты по версиям .NET. Программа **объединяет зависимости всех
  фреймворков**, потому что не знает, под какую платформу собирается проект. Поэтому
  у пакетов, которые поддерживают старый `netstandard1.x`, граф выходит большим: туда
  попадает `NETStandard.Library` и десятки системных пакетов, ненужных современному .NET.
- Каждый пакет хранится в графе **в одной версии** – той, что встретилась первой.
  NuGet при конфликте берёт наибольшую из минимальных версий.
- Из-за этого в настоящем репозитории иногда находятся «циклы», которых нет для конкретного
  фреймворка. Например, у `Serilog.Sinks.Console 6.0.0` (без ограничения глубины) программа
  находит `System.Net.Http -> System.Diagnostics.DiagnosticSource`.

## Тестовый репозиторий

Чтобы проверять программу без интернета, можно описать свой маленький «репозиторий» в текстовом
файле. Каждая строка – пакет и через двоеточие его зависимости. Пакеты называются заглавными
латинскими буквами, всё после `#` – комментарий:

```
A: B C
B: D
C: D
D:
```

Пакет, который упомянут только как зависимость, считается пакетом без зависимостей.
Готовые примеры лежат в папке [examples](examples):

- `basic.txt` – «ромб»: B и C оба зависят от D;
- `cycle.txt` – цикл A → B → C → A и пакет, зависящий сам от себя;
- `deep.txt` – длинная цепочка A → B → … → H для проверки `--max-depth`;
- `project.txt` – «приложение» с библиотеками для проверки `--filter`.

## Сборка и тесты

Понадобятся Java 21 или новее, Maven и утилита D2 (на macOS: `brew install maven d2`).

```bash
make build   # собрать программу
make test    # запустить тесты
make clean   # удалить всё, что получилось при сборке
```

Запускать удобнее всего через `./run.sh`: он сам пересоберёт программу, если код поменялся.
На Windows то же самое делает `run.bat` с теми же параметрами, например
`run.bat --package Newtonsoft.Json --package-version 13.0.3`. Он собирает программу при каждом
запуске, поэтому стартует на пару секунд дольше.
Тесты не требуют интернета: вместо nuget.org они поднимают локальный HTTP-сервер.
Два теста, которые вызывают настоящую `d2`, пропускаются, если она не установлена.

### Тестовый репозиторий

Цикл и пакет, зависящий сам от себя:

```
$ ./run.sh --test-mode --repo examples/cycle.txt --package A --ascii-tree --output test-cycle.svg
A
└── B
    └── C
        ├── A (цикл)
        ├── D
        └── E
            └── E (цикл)
```

Без `--ascii-tree` граф печатается списком:

```
$ ./run.sh --test-mode --repo examples/deep.txt --package A --max-depth 3
Граф зависимостей пакета A (пакетов: 4):
  A -> B
  B -> C
  C -> D
  D -> (не раскрыт: достигнута максимальная глубина)
```

Фильтр: без `TESTKIT` пропадают и `MOCK` с `ASSERT`, потому что к ним можно прийти только через него:

```
$ ./run.sh --test-mode --repo examples/project.txt --package APP --filter TEST
Граф зависимостей пакета APP (пакетов: 7):
  APP -> WEB, DATA
  WEB -> HTTP, JSON
  HTTP -> NET
  NET -> нет зависимостей
  JSON -> нет зависимостей
  DATA -> SQL, JSON
  SQL -> NET
```

## Сравнение с настоящим NuGet

Для сравнения я создал пустой консольный проект (.NET SDK 10.0.403, платформа `net10.0`),
добавил в него пакет через `dotnet add package` и посмотрел, что выбрал NuGet. Штатных
средств, которые рисуют граф картинкой, у .NET нет, поэтому сравнивал с текстовыми:
`dotnet list package --include-transitive` (плоский список) и `dotnet nuget why`
(дерево путей до заданного пакета).

**Microsoft.Extensions.Logging 8.0.0.** dotnet подтянул 6 пакетов. `dotnet nuget why`
для `DependencyInjection.Abstractions` показывает три пути к нему – через `DependencyInjection`,
`Logging.Abstractions` и `Options`, – ровно те же связи, что и на картинке depviz.

Без фильтра у depviz в графе 88 пакетов: те же шесть плюс `Microsoft.Bcl.AsyncInterfaces`,
`System.*`, `runtime.*` и `NETStandard.Library`.

**Serilog.Sinks.Console 6.0.0.** У dotnet 2 пакета: `Serilog.Sinks.Console` и `Serilog 4.0.0`.
У depviz без ограничения глубины – 82.

**Newtonsoft.Json 13.0.3.** dotnet не подтянул ни одной зависимости, а depviz находит
`NETStandard.Library` и всё, что за ним.

Почему так:

1. **Платформа.** dotnet берёт из `.nuspec` только группу зависимостей для своей платформы
   (`net8.0` или `net6.0` подходят для `net10.0`), а для неё у этих пакетов зависимостей
   почти нет. depviz объединяет группы всех фреймворков, в том числе `.NETFramework4.6.2`,
   `.NETStandard1.0` и `.NETStandard2.0`.
2. **Версии.** NuGet выбирает одну версию на пакет, и если её просят разные пакеты, берёт
   наибольшую из минимальных. depviz берёт ту версию, которую встретил первой. Поэтому
   в полном графе `Microsoft.Extensions.Logging` у depviz оказывается
   `System.Diagnostics.DiagnosticSource 4.3.0` (первый раз он встретился глубоко внутри
   `NETStandard.Library`), хотя сам Logging для старых платформ просит `8.0.0`.
3. **Повторы.** `dotnet nuget why` показывает каждый путь до пакета полностью, поэтому
   `DependencyInjection.Abstractions` в его дереве встречается три раза. depviz раскрывает
   пакет один раз, а дальше ставит `(*)`.

Если оставить у depviz только пакеты, которые есть и у dotnet, связи между ними совпадают.

На этапе 4 программа ещё печатала порядок загрузки (топологическую сортировку графа).
По заданию этот режим нужен был только на том этапе, поэтому в итоговой версии его нет.
Его можно посмотреть в истории коммитов. Сравнение тогда дало тот же результат: на общих
пакетах порядок совпадал с порядком, построенным по графу из `dotnet restore`, а различия
объяснялись теми же причинами.
